### Spec (don't look at Days 7 to 12)

**Models**: `Category`, `Post`, `Comment`, `Like`, with `Post.status` as `TextChoices`.

**Endpoints**

| Endpoint | Behavior |
|---|---|
| `POST /api/auth/register/` | creates user, returns token |
| `POST /api/auth/login/` | returns token |
| `GET /api/posts/` | list, paginated 10/page, `?page_size` capped at 50 |
| `POST /api/posts/` | create (auth required), author from `request.user` |
| `GET/PUT/PATCH/DELETE /api/posts/{slug}/` | detail by slug; only the author or staff can modify |
| `POST /api/posts/{slug}/like/` | like a post (idempotent) |
| `GET/POST /api/posts/{slug}/comments/` | list and create comments |
| `GET /api/posts/?search=&category=&ordering=` | search, category filter, ordering |

**Rules**
- Anonymous users can read published posts only.
- Authenticated users also see their own drafts.
- Title must be at least 5 characters. A published post needs a body of at least 50 characters.
- The list serializer is lighter than the detail serializer.
- `comment_count` and `like_count` must not cause N+1 queries.
- A custom signal fires when a post becomes published.

## Part 3: Write a custom permission without the docs (15 min)

Close everything and write each one. Use a scratch file.

1. **`IsAuthorOrReadOnly`**: anyone can read; only the author (or staff) modifies.
2. **`IsAdminOrReadOnly`**: anyone can read; only staff writes. This is for a `CategoryViewSet`.
3. **`IsOwnerOfLike`**: a `Like` has `user`, not `author`; only that user can delete it.
4. **`CanCommentOnPublished`**: block `POST` to comments when the post is a draft.
5. **Bonus**: a permission with a custom `message`.

<details>
<summary>Answers</summary>

```python
from rest_framework import permissions


class IsAuthorOrReadOnly(permissions.BasePermission):
    message = "You can only modify your own content."

    def has_permission(self, request, view):
        return (
            request.method in permissions.SAFE_METHODS
            or bool(request.user and request.user.is_authenticated)
        )

    def has_object_permission(self, request, view, obj):
        if request.method in permissions.SAFE_METHODS:
            return True
        return request.user.is_staff or obj.author_id == request.user.id


class IsAdminOrReadOnly(permissions.BasePermission):
    def has_permission(self, request, view):
        return request.method in permissions.SAFE_METHODS or bool(
            request.user and request.user.is_staff
        )


class IsOwnerOfLike(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):
        if request.method in permissions.SAFE_METHODS:
            return True
        return obj.user_id == request.user.id


class CanCommentOnPublished(permissions.BasePermission):
    message = "You cannot comment on an unpublished post."

    def has_permission(self, request, view):
        if request.method == "POST":
            post = view.get_post()
            return post.status == post.Status.PUBLISHED
        return True
```
</details>

**Check yourself**

1. When does `has_object_permission` run, and when does it not? (Only when the view calls `get_object()` or `check_object_permissions`; never on `list` or `create`.)
2. Why pair it with `IsAuthenticated`, or write `has_permission` yourself? (Because the object check never runs on `create`, and anonymous users would otherwise reach the view.)
3. Why `obj.author_id` instead of `obj.author`? (No extra query to load the author.)
4. What does `IsAdminUser` actually check? (`is_staff`, not `is_superuser`.)
5. A user gets 403 where you expected 401. What's the likely cause? (`SessionAuthentication` listed first, so there's no `WWW-Authenticate` challenge header.)

If you got 1, 2, and 5 right, you understand the part most people get wrong.

## Part 4: DRF ViewSet vs FastAPI route

Since you already compared the ORMs on Day 6, here's the framework-level comparison. They solve overlapping problems from opposite directions: DRF is **batteries included**, and FastAPI is **type-driven and minimal**.

### The same endpoint in FastAPI

```python
from fastapi import Depends, FastAPI, HTTPException, Query
from pydantic import BaseModel, ConfigDict, Field
from sqlalchemy import select
from sqlalchemy.orm import Session, selectinload

app = FastAPI()


class PostOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: int
    title: str
    slug: str


class PostUpdate(BaseModel):
    title: str | None = Field(default=None, min_length=5)
    body: str | None = None


@app.get("/posts", response_model=list[PostOut])
def list_posts(
    search: str | None = None,
    page: int = Query(1, ge=1),
    page_size: int = Query(10, le=50),
    db: Session = Depends(get_db),
):
    stmt = select(Post).order_by(Post.created_at.desc(), Post.id.desc())
    if search:
        stmt = stmt.where(Post.title.ilike(f"%{search}%"))
    stmt = stmt.limit(page_size).offset((page - 1) * page_size)
    return db.scalars(stmt).all()


@app.patch("/posts/{slug}", response_model=PostOut)
def update_post(
    slug: str,
    data: PostUpdate,
    user: User = Depends(get_current_user),   # you write this (JWT/OAuth2)
    db: Session = Depends(get_db),
):
    post = db.scalar(select(Post).where(Post.slug == slug))
    if post is None:
        raise HTTPException(404, "Not found.")
    if post.author_id != user.id and not user.is_staff:
        raise HTTPException(403, "You can only modify your own content.")
    for field, value in data.model_dump(exclude_unset=True).items():
        setattr(post, field, value)
    db.commit()
    return post
```

Compare that with DRF's `PostViewSet`, where the equivalent is `queryset`, `serializer_class`, `filterset_class`, and `permission_classes`.

### What's easier in each

| Area | DRF | FastAPI |
|---|---|---|
| **Standard CRUD** | **Much easier.** One `ModelViewSet` plus a router gives six endpoints | You write every route, query, and 404 check |
| **Admin, auth, users** | **Built in** (admin, sessions, permissions, tokens) | You assemble it (OAuth2/JWT helpers, your own user table, SQLAdmin or similar) |
| **Filtering, search, pagination** | **Plug-ins** (`django-filter`, `SearchFilter`, paginators) | Hand-written, or libraries like `fastapi-pagination` |
| **Migrations** | `makemigrations`, built in | Alembic, configured yourself |
| **Request validation** | Serializer classes, with more ceremony | **Easier.** Type hints are the validation (Pydantic), with no separate class per concern |
| **API docs** | Needs `drf-spectacular` or similar | **Automatic**, interactive at `/docs` |
| **Async and concurrency** | Possible (async views exist) but the ORM and ecosystem are mostly sync | **Native.** Built for `async def` and high concurrency |
| **Dependency injection** | Permission classes, mixins, and `get_queryset` hooks | **`Depends()`** is explicit, composable, and easy to test or override |
| **Per-endpoint flexibility** | Fighting the viewset abstraction when you leave CRUD | **Easier.** Each route is just a function |
| **Editor support and type safety** | Dynamic; serializer fields aren't type-checked | **Better.** Types flow from the request to the response model |
| **Learning curve** | Many concepts (serializers, viewsets, routers, backends) before the first thing works | Smaller; the first endpoint takes a few lines |
| **Conventions** | Strong, consistent across projects | Few; project structure is up to you, so codebases vary |
| **Maturity of the ecosystem** | Very mature, with huge numbers of packages | Younger, but growing fast |

### Where the abstractions differ

1. **Serializer vs Pydantic model.** A DRF `ModelSerializer` is generated from the model and also handles saving (`create`/`update`). Pydantic models are pure validation and shape. Persisting is your job, and with SQLAlchemy the ORM model and API schema are separate classes you keep in sync.
2. **Permissions vs dependencies.** DRF has a fixed two-hook permission system (`has_permission`, `has_object_permission`). In FastAPI, auth is just a dependency that either returns a user or raises, and object-level checks are ordinary `if` statements. That's simpler but easier to forget.
3. **Router vs decorators.** DRF generates URLs from a viewset. FastAPI maps a URL to a function you write, and that explicitness is both its strength and its cost.
4. **Session and transactions.** In DRF the ORM handles connections implicitly. In FastAPI you manage the SQLAlchemy `Session` through a `get_db` dependency, which ties back to Day 6's comparison.

### Rule of thumb

- Choose **DRF** for a CRUD-heavy product with an admin, users, and relational data where you want to ship quickly.
- Choose **FastAPI** for microservices, ML or async-heavy workloads, thin APIs over existing data, or when you want typed, auto-documented endpoints and are happy to assemble the rest.

## Common gotchas

- **Peeking too early.** Ten real minutes of struggle beats reading the answer after two.
- **Rebuilding in the old project.** You'll copy-paste from memory of your own files. Use a fresh one.
- **Calling a signal test "passing" without `captureOnCommitCallbacks`.** The test can pass because the callback never ran.
- **Testing only the happy path.** Half of today's value is the 401, 403, 400, and 404 cases.
- **Comparing frameworks by feature count.** Compare by what you'd have to write yourself, which is what actually costs time.
- **Treating filters as security.** Visibility belongs in `get_queryset()` and permissions.
